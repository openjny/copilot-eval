# Feature Specification: ローカルでの条件別 Copilot 比較

**Feature Branch**: 未作成。feature の識別子は `001-local-comparison`。

**Created**: 2026-09-12

**Status**: Draft。既存のローカル比較要件の移行先。承認・実装・技術検証は未実施。

**Input**: 既存のプロダクト方針とユースケース・要件を基に、利用者がローカルで同じタスクを複数条件で実行し、品質・使用量・料金を比較する機能を定義する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 比較条件を用意して事前確認する (Priority: P1)

対応する既存 UC: UC-003（構成チェック）、UC-004（実行予定）、UC-005（比較準備）。

利用者は手元の資料やプロジェクトとタスクを指定し、モデル・effort が異なる条件を用意する。実行前に設定の誤りと実行予定を確認したい。

**Why this priority**: 条件を取り違えた比較や、意図しない実行による費用の発生を防ぐため。

**Independent Test**: 1タスク・2条件・各2回の定義から計4回の実行予定を得る。Copilot の実行なしで、誤った設定と適用条件を確認できる。

**Acceptance Scenarios**:

1. **Given** 同じモデルの effort だけが異なる2条件と各2回の反復指定、**When** 実行予定を確認する、**Then** 条件・反復番号を区別した計4回の実行予定と各適用構成が示され、タスクは実行されない。
2. **Given** 存在しない配置元または不正な反復回数、**When** 設定チェックまたは実行開始を行う、**Then** 修正箇所が示され、既知の構成エラーを残したままタスクを開始しない。
3. **Given** スキルを含まない比較定義、**When** 設定を確認する、**Then** スキルがないことだけを理由に拒否されない。
4. **Given** 複数条件の定義、**When** 条件と反復回数を絞る、**Then** 元の定義を変更せず、選択後の実行予定を確認できる。
5. **Given** レビューはモデルA・B、解説文はモデルB・Cを各3回、全体の並列上限2件とした一つの定義、**When** 実行予定を確認する、**Then** タスクごとの条件に従う計12回の実行予定と共通の並列上限が示され、条件群が違うことだけで定義の分割を要求されない。
6. **Given** 3回の反復予定のうち1回目が完了し、2回目はエラー後に再試行して完了し、3回目は未着手の状態、**When** 予定と結果を確認する、**Then** 3件の Task Run が反復1・2に対応し、完了した反復は2回、未着手は1回と分かり、再試行を独立反復として数えない。
7. **Given** プロンプトだけのタスク依頼と、プロンプトに資料ファイルのアタッチメントを添えたタスク依頼、**When** 実行前チェックを行う、**Then** どちらも指定でき、アタッチメントの省略だけでは拒否されず、プロンプトの指定がない場合は構成エラーとして報告される。

### User Story 2 - 同じ初期状態から実行して記録を得る (Priority: P1)

対応する既存 UC: UC-001（実行・記録）、UC-009（Windows の実務タスク）。

利用者は比較を実行し、各条件で何が起きたかを、評価基準がなくても確認したい。

**Why this priority**: 比較の前提をそろえ、失敗を含めた判断材料を得るため。

**Independent Test**: 有効な比較定義を入力し、最初の試行がファイルを変更しても次の試行へ持ち越されず、各試行の結果と記録が残ることを確認する。

**Acceptance Scenarios**:

1. **Given** 各 Task Run の初期状態を指定した環境、**When** 2条件を順に実行する、**Then** 各 Task Run は指定された状態から開始し、前回の変更を継承しない。
2. **Given** 評価基準なしの実験、**When** 実行する、**Then** 実行状態・記録・取得済み使用量・保存対象の成果物が残り、評価は未評価と表示される。
3. **Given** ある Task Run だけが失敗し、ほかは実行可能な状態、**When** 比較を継続する、**Then** 失敗を記録に残し、実行可能な残りの結果も得られる。
4. **Given** 対応する Windows 環境と準備済みツールを使うプロジェクト、**When** タスクを実行する、**Then** Windows 上で実行・検証され、実際の OS とツール構成を確認できる。
5. **Given** 実行を開始したが環境の準備手順が失敗した状態、**When** 結果を確認する、**Then** Task Run に条件・準備失敗の理由・SDK セッション未作成が記録され、Copilot は実行されず、モデルの品質の不合格として扱われない。

### User Story 3 - 品質と使用量を比較して原因を調べる (Priority: P1)

対応する既存 UC: UC-002（評価基準の改善）、UC-006（比較）、UC-007（原因調査と試し直し）。

利用者は条件別の評価と使用量を比べ、気になった結果から個別の記録へ進み、次に試す変更を判断したい。

**Why this priority**: 単発の成功や平均値だけでモデルやカスタマイズの効果を判断しないため。

**Independent Test**: 正常・失敗・未評価・判定不能・使用量欠測を含む既知の記録を使い、条件別集計と元の記録への追跡を確認する。

**Acceptance Scenarios**:

1. **Given** 同じモデルで effort が異なる結果、**When** 比較を確認する、**Then** 条件を混合せず、評価ポイント・使用量・料金・対象件数を並べて確認できる。
2. **Given** 評価処理の失敗と、正しく評価され不合格だった試行、**When** 結果を見る、**Then** 判定不能と不合格が区別され、評価失敗をゼロ点で埋めない。
3. **Given** AIC またはトークン情報が取得できない試行、**When** 集計を見る、**Then** 欠測と対象件数が分かり、実測ゼロや確定料金として表示されない。
4. **Given** 実行が途中終了したが評価に必要な記録は残っている、**When** 評価する、**Then** 終了状態だけで除外せず、指定基準に従う判定を得る。
5. **Given** 保存された個別結果、**When** 詳細を確認する、**Then** 適用条件・指示・行動・ツール応答・検証コマンドの出力を追跡でき、取得不能・省略・秘匿は区別される。
6. **Given** 同じタスク・モデル・設定で対応する CLI ランタイム版だけが異なる2条件、**When** 実行して比較する、**Then** 指定版と観測できた実行版を記録し、版の異なる結果を混合せず、品質・使用量と個別記録を確認できる。
7. **Given** 昨日と今日の別の実験実行に属する Task Run、**When** それらを選んで比較する、**Then** 各 Task Run の保存済み条件と関連評価へたどれ、元の定義が変更されても過去の適用条件は変わらず、新たな実行や評価は発生しない。
8. **Given** キャッシュ利用量を取得できた Task Run と取得できなかった Task Run、**When** 使用量・料金を比較する、**Then** キャッシュ効果を含む実消費を確認でき、観測したキャッシュ利用量と条件を対応づけて分析でき、取得不能は利用ゼロと区別される。
9. **Given** Task Run 後に元のプロンプト・アタッチメント・スキル・設定が編集または削除された状態、**When** 当該 Task Run の条件を確認する、**Then** 保存内容または保持された不変の版から当時の内容を読め、秘密情報の秘匿・省略は識別できる。

### Edge Cases

- 未対応のモデル・effort・CLI ランタイム版を黙って置換しない。静的に分からない不適合は、実行時に該当条件の失敗として報告する。
- 条件名が同じでも構成が異なる結果や、尺度が異なる評価を暗黙に同じ平均へまとめない。
- 認証不足や環境準備の失敗を、タスクの低品質や評価の不合格として扱わない。
- 記録が不足して評価できない場合は、評価基準ごとの判定不能と理由を残す。
- 定義した準備手順が失敗した環境で、そのまま Copilot の実行を始めない。
- 初期状態の分離とネットワーク隔離を同一視しない。適用できた制限と未確認の範囲を示す。
- 後片付けに失敗した場合は、残った管理対象資源を報告する。元のプロジェクトや共有サービスを削除しない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 利用者はタスク、タスク依頼、配置物、準備手順、比較条件、反復回数、任意の評価基準を指定し、本体の変更なしでローカル比較を実行できなければならない。タスク依頼はプロンプトを必須とし、資料ファイルのアタッチメントを任意で指定できなければならない。一つの実験でタスクごとに異なる条件群を指定できなければならない。
- **FR-002**: スキルまたは Git リポジトリの存在を必須にせず、既存の資料・コードを環境の一部として扱わなければならない。
- **FR-003**: モデル・effort・CLI ランタイム版・指定した primitives とツール利用方針を明示し、独自の意味へ書き換えたり、暗黙に別の設定へ置換したりしてはならない。ツールなしの条件も指定できなければならない。
- **FR-004**: 実行前チェックと実行予定の確認を提供し、既知の構成エラー、対象件数、適用条件、未検証の実行時条件を示さなければならない。予定確認だけでは環境構築やタスク実行を開始してはならない。
- **FR-005**: タスク・条件・反復を元の実験の編集なしで絞れなければならない。指定された並列上限を守り、実際に選択した対象と上限を記録しなければならない。本体は条件の偏りを抑える実行順序を組み、予定と実際の順序を記録しなければならない。順序の決め方と並列実行時の検証方法は設計で具体化する。
- **FR-006**: 各 Task Run の開始環境を指定した初期状態から用意し、前回の変更・会話・実行結果を暗黙に継承または再利用してはならない。
- **FR-007**: 実験実行・Task Run を識別し、各 Task Run からタスク、タスク依頼、比較条件、環境、エージェント構成、反復番号、再試行元、実行状態、記録、成果物、計測値、関連評価へたどれなければならない。未着手の反復予定も保持しなければならない。保存済みの宣言・適用情報は、元の定義の変更によって書き換えてはならない。持ち込まれたプロンプト・アタッチメント・スキル・設定は、秘密情報を除き、当時の内容を後から読める形で保持しなければならない。
- **FR-008**: 設定として指定された構成と実行時に観測した情報を区別し、実行 OS・シェル・主要ツールの版と、制御・観測できなかった範囲を記録しなければならない。
- **FR-009**: 評価なしの実行と、実行に続く評価・集計を選べなければならない。未評価は実行失敗や不合格と区別しなければならない。
- **FR-010**: 利用者は標準の評価基準を明示的に選び、基準と判定処理を本体の変更なしで調整・追加できなければならない。標準基準には測定対象・判定方法・必要入力・結果の意味を示し、すべてを自動適用しない。
- **FR-011**: 評価は正常完了を一律の前提にせず、利用可能な入力と指定基準に従わなければならない。未評価・判定不能・不合格を区別し、項目単位の結果と理由を残さなければならない。
- **FR-012**: トークン・AIC・料金を条件別に確認できなければならない。各値の単位、取得元、実測・推定・欠測の区別を示し、タスク実行と評価処理の使用量を混同してはならない。キャッシュ効果を含む実消費を比較し、観測できたキャッシュ利用量と利用状況を実行条件・記録に対応づけて分析できなければならない。
- **FR-013**: モデル名だけで集約せず、effort・CLI ランタイム版・primitives・環境を含む比較条件を区別しなければならない。評価ポイント別の結果、集計対象数、失敗・未完了・欠測、各回の結果を確認できなければならない。実験・実験実行をまたいで Task Run と関連評価を選び、比較できなければならない。
- **FR-014**: 条件別の結果から、対応する指示、行動、ツール応答、検証コマンドの標準出力・標準エラー、保存対象の成果物へたどれなければならない。
- **FR-015**: 一つの Task Run の失敗だけを理由に、実行可能なほかの Task Run や未着手の反復予定を中止してはならない。共通の前提が失われた場合は、継続不能の理由と取得済み結果を残さなければならない。
- **FR-016**: CLI で比較を操作し、結果を機械可読形式で取得できなければならない。結果の閲覧は新たな実行や評価を発生させてはならない。
- **FR-017**: 本 feature の環境対応は [NFR-001](../../docs/nonfunctional-requirements.md)に従う。具体的な確認シナリオは Story 2 と SC-006 を使用する。
- **FR-018**: 設定・記録・後片付けには [NFR-005](../../docs/nonfunctional-requirements.md)を適用し、保存対象の記録・成果物を保持しなければならない。

### Key Entities *(include if feature involves data)*

定義は [共通ドメインモデル](../../docs/domain-model.md) を参照する。本 feature は実験・タスク・比較条件、実験実行・Task Run、実行記録・評価基準・評価を使用する。固有の追加概念は定義しない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1タスク・2条件・各2回の確認例で、計4回の反復予定と実績が対応し、異なる effort の結果が同じ条件へ混ざらない。再試行を含む場合も反復番号ごとに対応づけられる。
- **SC-002**: 意図的なファイル変更を伴う確認例で、後続の Task Run への変更持ち越しが0件である。
- **SC-003**: 正常・実行失敗・未評価・判定不能・欠測を含む確認例で、全件が正しい状態で識別され、失敗や欠測をゼロ点・使用量ゼロとして補完しない。
- **SC-004**: すべての表示結果を元の Task Run・反復番号・適用条件へ追跡できる。入力済みの既知の使用量と評価値が、対象条件の集計にのみ反映される。
- **SC-005**: 利用者が本体を変更せず、1タスクの準備・事前確認・実行・結果比較を完了できることを人間のレビューで確認する。
- **SC-006**: Linux と Windows の対応構成それぞれで、コード・コマンドを使う1件以上のタスクを実行・検証し、OS と制限の適用範囲を結果から確認できる。

## Assumptions

- アクターは copilot-eval の利用者とする。利用者がエージェントに操作を代行させることも想定し、評価対象のエージェントとは区別する。人間向けの表示を要約しても、代行するエージェントが取得する条件・状態を暗黙にしない。具体的な操作契約は共通設計で定める。
- 実験を記述したファイル・コードと独自の評価処理は信頼済みの入力とする。生成されるコマンドの安全性まで保証するものではない。
- 利用者は Copilot の利用権限、必要な認証、プロジェクトのライセンス、準備手順を用意する。
- モデル提供側や外部情報源の変化による出力差はあり得る。初期状態の管理は、LLM 出力の一致を保証しない。
- 既存IDの所有先は [移行索引](../README.md)を参照する。分割・移行は実装や全要件の承認を意味しない。
- constitution と共通ドメインはレビュー用草案、全体設計の具体化は TBD。これらとの適合は計画開始前の確認事項とする。

### Scope and Adjacent Features

- 本 spec はローカルでの基本比較と取得済み結果の確認を対象とする。第一段階全体をこの1件で定義しない。
- 初期の環境準備は、指定された手順を適用する範囲とする。準備手順の自動生成は後続候補として扱う。
- 第一段階に必要な隣接機能は [実行・環境管理](../002-execution-management/spec.md)で管理する。
- それらが未提供の状態では、第一段階全体の完成とは扱わない。本 spec の草案作成は提供段階の変更を意味しない。
- 隣接機能の設計時には、反復予定と Task Run の対応、再試行元の識別、失敗履歴、使用量の保存責任、終了後の評価可能性を共通設計として確認する。
- 設定または評価基準を変更して試し直す場合は、元の結果を上書きせず、新しい実験実行でタスクから実行する。評価だけの再実施は後続の検討とする。
- Web ダッシュボード、遠隔・分散実行、PR 連携、自動改善、自動的な勝者選定、高度な統計検定は本 spec に含めない。
- 対応 OS・ツールチェーンの具体的な版、通信制御、計測可能範囲、保存形式、判定形式、標準評価基準の収録内容は、共通設計と技術検証で具体化する。

### 比較例の候補

実験の構成例であり、全実験へ固定のツールや公開範囲を強制しない。サンプルの収録対象と提供時期は TBD。

| 題材 | そろえる条件と変える条件 | 確認したいこと |
| --- | --- | --- |
| 日本語の文章生成 | 同じローカル資料・テーマ、ツール無効、タスク遂行の外部情報取得なしでモデルを切り替える。モデル接続に必要な通信は別に扱う | 日本語の自然さと使用量。資料をツールなしで入力へ渡す方式は TBD |
| 実在するバグのレビュー | Issue と修正履歴があるリポジトリの修正前コミットを固定し、通常のツール利用下でモデル・effort を変える | バグの発見と修正提案の妥当性。修正後の情報は採点根拠とし、対象コードだけを見せる条件では Git 履歴や外部の正解情報を公開しない |
| 言語・スキルの違い | 同じタスク・モデル・effort で、日本語／英語出力やスキルの有無を変える | 精度を維持しながら使用量を減らせるか |
| RTK 等の出力圧縮 | 通常のコマンドと `rtk ls` 等のラッパー経由を比較する。必要なツールは実験に指定した準備手順で導入する | 圧縮されたコマンド出力でもタスクの精度を維持できるか |

行動を判定する基準も指定できる。例えば、回答の正確さとは別に、調査中にリソースを変更した行動を評価する。禁止操作を実行前に防ぐこととは区別する。

### 補足と TBD

- 初期は一回のタスク依頼を扱い、その中で複数のモデル・ツール呼び出しが発生し得る。後から追加メッセージを送る会話シナリオは将来候補。
- 初期から SDK の BYOK 接続設定と、本体に専用項目がない SDK 設定の直接指定を扱う。ランタイム版も比較条件にできるようにする。対応版と本体の計測・停止制御との整合は [全体設計](../../docs/architecture.md) で検討する。
- 比較例からの開始と独自実験の双方を扱う。収録例、設定の明示範囲、観測できないデフォルト、保存形式、構成チェックの具体項目は TBD。確認処理が外部接続や利用者の実装した準備手順・評価器の読込を伴う範囲も設計で定める。
- 標準基準は作成負担の軽減と意味の理解・再利用を目的とする。収録したことだけで妥当性が保証されるわけではない。基準の種類、利用者が実装した評価器の参照方法は TBD。
- 評価基準の調査では Foundry の evaluator 一覧なども参考にするが、そのサービスへの依存や採用は未決。実在バグの自動収集、リポジトリと Issue からの実験構成生成も候補にとどめる。
- 評価の開始時点、環境を使う判定と後片付けの順序、項目単位のエラー情報、記録と成果物の保存対象は TBD。コマンド出力の保存だけでは当時の環境で再検証できるとみなさない。
- 共通の前提が失われた際の停止範囲、評価処理の並列度、使用量や金額を取得できない場合の表示は TBD。
- 比較結果を一つの総合点へ独自に重み付けしない。評価結果の必須フィールドと形式は TBD。将来の join は尺度や閾値を補正して数値を平均する案であり、単なる一括実行や合否の論理積ではない。
- 記録から改善案を提示する機能、複数回答を見比べる評価、人による採点、追加反復は後続候補であり、現時点の採用・提供時期は TBD。
- 資料ファイルをタスク依頼のアタッチメントとして指定することは初期範囲とする。画像・スクリーンショット等のマルチモーダル入力の対応は将来候補。専用の変換・生成機能や、評価・モックの専用リプレイコマンドを初期要件にしない。本文を保存せず点数だけを残すモードも初期範囲に含めない。
- 要求ごとの確認は各シナリオ・SC に対応づける。詳細な確認ID・担当・期限、文書全体の承認版は TBD。
