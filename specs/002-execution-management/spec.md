## User Scenarios & Testing

### UC-008: 実行状況を確認し、停止・再開する

- 提供段階: 第一段階。アクターは利用者。
- 目的: 比較開始後に別の作業を行い、後から状態を確認して不要な実行を止め、未完了分を続けられるようにする。
- 前提／入力: [ローカル比較](../001-local-comparison/spec.md)で用意した実験と実行ID。
- 操作と応答: 開始を受け付けた CLI は戻り、実行は継続する。別の操作で進行段階・件数・取得済み使用量・失敗理由を確認し、個別または全体へ停止を要求する。再開では元の条件を使う。
- 例外: 停止要求の受付と停止完了を区別する。取消し・低評価・上限到達を自動再試行しない。電源断後の自動継続は保証しない。
- 完了条件: 完了・未完了・失敗と後片付け状況を識別でき、再試行前の記録が失われない。

**Acceptance Scenarios**:

1. **Given** 実行を受け付けた状態、**When** 開始 CLI が終了する、**Then** 別の CLI から同じ実行の状態と取得済み結果を確認できる。
2. **Given** 使用量を消費して失敗した Task Run、**When** 再試行する、**Then** 元と同じ反復の消費済み量が残り、累積量に対して上限が適用される。
3. **Given** 一部が完了した比較、**When** 同じ条件で再開する、**Then** 完了分を再実行しない。条件変更時は別の比較として扱う。
4. **Given** サービスを含む実験、**When** 正常終了または停止する、**Then** 管理対象のサービスを片付け、取得済み記録を保持する。
5. **Given** 複数の Task Run が実行中、**When** 一つの反復の停止を要求する、**Then** 受付と停止完了を区別して確認でき、ほかの実行可能な反復は続行し、停止対象の記録と使用量も残る。
6. **Given** 低評価・明示的な停止・使用量上限到達のいずれかで終わった Task Run、**When** 自動再試行の対象を判定する、**Then** これらを理由に新しい Task Run を開始しない。
7. **Given** MCP または外部コマンドの固定モックと未定義呼び出しの応答方針、**When** 異なる比較条件で呼び出す、**Then** 同じ応答定義が適用され、未定義呼び出しは指定方針に従い、モデルごとの呼び出し順序は強制されない。
8. **Given** 明示指定したエラーで同じ反復を再試行し、設定した再試行回数に達した状態、**When** 再び同じ種類のエラーが起きる、**Then** 追加の自動再試行を行わず、各 Task Run の理由・使用量・記録と再試行元との関係を保持する。
9. **Given** 自動再試行の設定を省略した実行、**When** 通信障害で Task Run が終了する、**Then** 本体は自動再試行せず、終了理由と観測した事実を保存する。
10. **Given** 対象エラーと回数上限を明示した実行、**When** 対象エラーが発生し上限内で再試行する、**Then** 新しい Task Run を同じタスク・条件・反復番号に対応づけて保存し、再試行元の記録を保持する。対象外のエラーでは自動再試行しない。

## Requirements

意味と不変条件は [ドメインモデル](../../docs/domain-model.md#実験タスクと実行)を参照する。以下の既存IDを要求の正本として維持する。

- **REQ-008**: 設定したトークンまたは AIC 上限を、同じ実験実行・タスク・条件・反復番号に対応する Task Run の累積使用量に適用する。失敗と再試行も合算し、再試行で枠をリセットしない。目的は再試行による費用増加の抑制であり、途中終了後の評価可否はこの要件で決めない。
- **REQ-017**: 未完了分の再開は開始時の条件を使用する。タスク・環境・モデル等を変更した結果を元の比較へ混在させず、別実行として識別する。
- **REQ-019**: MCP と外部コマンドを実験に指定したモックへ差し替え、定義済み・未定義呼び出しの応答方針を指定できる。初期は固定応答。外部状態の変化を除く目的であり、モデル間の呼び出し順序は強制しない。
- **REQ-020**: 一台でも開始コマンドの応答後に処理を継続し、実行IDを使って別の CLI から進行状態と結果を取得できる。
- **REQ-021**: タスク遂行中に必要なサービスを実験で指定し、本体が起動・維持・終了を管理する。SDK 外のサービスも対象とし、事前の手動起動だけに依存しない。維持は無条件の再起動を意味しない。

停止・再試行の詳細要求: 個別と全体の停止、停止後の記録保持、管理対象のみの後片付けを提供する。本体の自動再試行はデフォルトで無効とし、利用者が対象エラーと回数上限を明示した場合だけ有効にする。理由・回数・各 Task Run の使用量と再試行元との関係を保持する。SDK 内部のリトライとは区別する。進行状態名、指定可能なエラーの分類・識別方法、原因不明時の評価方針は TBD。

タイムアウトと個別停止は、実験実行内のタスク・条件・反復番号ごとに扱う。停止した反復を自動再試行で再び動かさない。比較全体の使用量キャップは現行範囲に含めない。

実行中の行動と取得済み使用量を確認し、ほかの実行を続けたまま一件だけ停止できるようにする。使用量を取得できない接続先でも、指定されたキャップを黙って無効化しない。扱いの決定は下表の検証後とする。

調査用に明示指定した場合は実行環境を保持できるようにする。すべての失敗環境を自動保持せず、保持期限・費用・削除方法と利用者所有資源との区別を確認できるようにする。具体的な保持方式は TBD。

初期はローカルとモックを中心とし、実在する外部リソースを操作する実験は将来候補。実行先 VM の管理とは区別する。Azure 全体のシミュレーターや複雑なモック専用言語は要求しない。モックの対応不足による失敗・追加使用量はモデルの能力差と混同せず、応答選択の補助方式は TBD。

## Success Criteria

上記確認で、履歴の消失、条件の混在、再試行による消費枠リセットがないこと。正しいモック応答とサービスの開始・終了を追跡できること。検証環境・合格の詳細水準・担当・期限は TBD、全件未実施。

## Assumptions and Dependencies

[ローカル比較](../001-local-comparison/spec.md)の実行記録と初期状態管理に依存する。逆に第一段階全体の完成には本 feature も必要であり、分割によって要求を後続段階へ延期しない。設計は [共通アーキテクチャ](../../docs/architecture.md)、品質制約は [非機能要件](../../docs/nonfunctional-requirements.md)に従う。評価を始める順序と環境の後片付けを、両 feature をまたいで検討する。
