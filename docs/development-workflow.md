# 開発フロー

草案。次に何を確認して、どこまで作業するかを決めるためのガイド。文書の保存先と書き方は [文書管理ガイド](documentation-guide.md) を参照する。

## 変更に応じて始める

| 変更 | 最初に行うこと | Spec Kit の使い方 |
| --- | --- | --- |
| 新しい利用目的・独立した機能 | vision、共通モデル、関連 spec と境界を確認する | specify から開始する |
| 既存機能の意図した振る舞いの変更 | 所有する既存 spec と影響先を特定する | 既存 spec を直接編集または clarify で更新し、必要な plan・tasks を追従させる |
| 共通用語・ルール・全体設計の変更 | 影響する feature と既存判断を調べる | 共通文書の変更案を先に示し、関連する feature の計画へ反映する |
| 要求を変えない小さな不具合修正 | 既存要求と再現条件を確認する | 新規 spec は必須にせず、修正と回帰確認を記録する |
| 振る舞いを変えないリファクタリング | 既存契約と回帰リスクを確認する | 規模に応じて既存 plan・tasks を更新する。新しい仕様が必要と分かったら要求変更として扱う |
| 誤字、リンク、説明の整理 | 意味が変わらないことを確認する | 通常の文書修正でよい |
| 実現可能性の調査 | 判断したいこと、調査範囲、費用・環境変更の制約を決める | 調査と判断を同じ ADR に残す。調査だけで実装工程へ進まない |

## 共通モデルと feature を行き来する

具体的な利用場面を使い、利用者の操作と起きる出来事を説明する。その中で意味が曖昧な語を [ドメインモデル](domain-model.md) に整理し、複数機能の約束を [全体設計](architecture.md) で確認する。feature は、提供価値と受入れ確認がまとまる範囲にする。

例えば、停止・再試行・累積使用量上限・Windows・将来の遠隔実行は、複数の feature に分かれても実行の寿命と計測値の保存責任を一緒に検討する。全体設計を各 feature の plan から後付けで寄せ集めるだけにしない。

1 UC、1エンティティ、1コンポーネントを必ず1 spec にする規則は置かない。全体設計を完成させてから進むのではなく、次の変更に関わる境界を確認し、実装や検証で分かったことをモデルへ戻す。DDD の実装パターンやサービス分割は必要になってから選ぶ。

## Spec Kit に何を渡すか

以下はこのプロジェクトでの使い方であり、標準マニュアルの代わりではない。実行時はインストール済みのコマンド定義を確認する。現在の Copilot 連携では `/speckit-...` 形式を使用する。

### 共通の入力

どの工程でも、対象 feature、今回の目的、参照する正本と関連箇所、変更範囲、対象外、未確定事項、許可する操作、終了地点を伝える。文書が存在しない、またはテンプレートでしかない場合はその事実を示し、確定済みの前提を捏造しない。

共通文書はパスを書くだけでなく、必要なものを実際に読むよう指定する。全 spec を毎回読み込むのではなく、共通概念・契約・依存関係から関連先を選ぶ。調査した範囲と未確認の範囲を結果に残す。

| コマンド | 使うとき・渡す内容 |
| --- | --- |
| `/speckit-constitution` | 原則を制定・変更する。原則案、理由、参照する方針、影響範囲を渡す。未承認の案は案として残す |
| `/speckit-specify` | 新しい機能を定義する。利用者の目的、利用場面、対象外、共通モデル、関連 spec を渡す。spec と品質チェックリストを確認する |
| `/speckit-clarify` | 要求の曖昧さを解消する。既知の判断と変更してよい範囲を伝え、回答を spec へ反映する |
| `/speckit-checklist` | 要求の品質を点検する。対象と観点を指定する。動作テストの代わりにはしない |
| `/speckit-plan` | 要求の境界を確認して設計する。共通設計・品質制約・調査課題を渡し、feature の方式と共通設計への影響を確認する |
| `/speckit-tasks` | 計画を実装・検証作業へ分ける。採用する設計、依存関係、検証方針を渡す。ここで新しい要求を追加しない |
| `/speckit-analyze` | spec・plan・tasks が揃ったら整合性を見る。共通モデルと関連 spec も指定する。結果は読み取り専用の指摘 |
| `/speckit-implement` | 実装を依頼する。対象タスク、許可する操作・費用、検証と停止条件を渡す。実施した作業だけを完了にする |
| `/speckit-converge` | 実装後の不足を見る。対象 feature と完了基準、実行できる検証を渡す。tasks の追記を確認し、許可された範囲で実装を続ける |

標準の analyze は主に現在の feature 内の分析であり、全 spec の横断監査を自動実行するものではない。必要な関連文書を入力へ追加し、十分に確認できなければ別の横断レビューを行う。

1回の specify で扱う feature は1件。複数の spec を置くことはできるが、同じワークスペースで作業対象を取り違えないよう、`.specify/feature.json` と対象パスを確認する。移行のために直接作った草案を、標準フローの確認まで完了した spec とみなさない。

### 指示例

```text
/speckit-specify
目的: 利用者が同じタスクを異なるモデル・effort で比較できるようにする。
参照: 現在のプロダクト方針、共通ドメインモデル、関連する既存 spec を読む。
範囲: ローカルでの準備・実行・記録・結果比較。
境界: 停止・再試行・上限管理との依存を明記する。未実装だからといって要求を削らない。
出力: 日本語の spec と品質チェックリスト。既存IDとの対応を残す。
停止: 草案の作成と確認まで。plan・tasks・実装には進まない。
```

```text
/speckit-plan
対象: レビュー済みの feature spec。
参照: constitution、共通モデル、全体アーキテクチャ、関連 feature を読む。
重点: Windows と Linux、実行の寿命、使用量・失敗履歴、評価前の後片付け順序。
方式: 既存の制約を守り、未確定部分は代替案と判断根拠を示す。
制限: 有料API、クラウド作成、重いパッケージの導入は実施しない。
出力: feature の設計案と、共通設計への変更提案を区別する。
停止: 設計・調査結果の報告まで。tasks・実装には進まない。
```

例中の参照は、実行時に [文書管理ガイド](documentation-guide.md) から実在する正本のパスと対象箇所へ具体化する。

### Specify CLI とエージェントコマンドの区別

`specify init`、`specify check`、`specify preset ...` 等は、導入・設定を扱う端末の CLI コマンドである。要求を記述する `/speckit-specify` 等とは役割が異なる。

- 初期化・更新・拡張導入は必要なときだけ行い、各 feature の開始時に init を再実行しない。
- 強制初期化や更新の前に、既存の constitution・独自テンプレート・生成指示への影響を確認する。
- 拡張や preset は、版、依存、変更するコマンド、合成・上書きの結果を確認してから導入する。
- `specify check` の成功を、製品や spec の検証成功とは扱わない。
- Git の初期化、ブランチ作成、コミット、push は工程名から暗黙に許可されたと解釈しない。

## 既存の spec を育てる

本草案では Living Spec を基本運用として提案する。既存機能の意図した振る舞いが変わるときは、その spec を先に更新し、plan・tasks・実装・検証を追従させる。これは Spec Kit の CLI 設定ではなく、プロジェクトの運用上の選択である。

- 関連 feature を調べ、同じ要求の言い換えなら既存IDを維持して更新する。独立した提供価値や別の境界がある場合に新規 feature を作る。
- 実装中の発見は記録し、要求変更、設計変更、作業の修正のどれかを分類する。コードや tasks だけを変更して spec と矛盾したままにしない。
- plan・tasks を再生成する前に、必要な判断理由と実施済み検証の証跡を保存する。作業の完了履歴を誤って未実施へ戻したり、未実施を完了へ引き継いだりしない。
- 既存の UC-ID・REQ-ID を改番しない。feature 内の FR・SC・Task ID は feature の識別子と組み合わせて参照する。
- spec の置換・分割・廃止では、後継、対象範囲、IDの対応を残す。新旧両方を現在の正本として提示しない。
- feature が増えたら、specs の索引に目的・状態・依存・正本へのリンクを置く。要件本文の別台帳は作らない。

## レビューと作業範囲

実装に進む前に、対象の要求と計画の意図を確認する。共通モデル・品質制約・原則を変える場合は、関連 spec・契約・テストへの影響を調べる。エージェント指示や本フローの変更でも、参照する正本と生成済みコマンドの整合を確認する。

重大な範囲変更、原則の例外、全体設計の変更は理由と影響を提示して本プロジェクトの開発者の判断を求める。通常の作業選択まで逐一質問せず、一連の作業が許可されていればその範囲で進める。「spec の作成まで」の依頼で plan や実装へ進んだり、「次へ」を未回答事項への同意と解釈したりしない。

レビューした変更と判断内容が後から分かればよく、毎回専用の承認書を作る必要はない。生成・承認・実装・動作確認は区別し、実行していない検証を成功と報告しない。

## ADR を読む・残す

**読むとき:** 既存判断の変更・撤回、例外、代替案の再検討、理由や制約の確認、文書間の矛盾の解消が必要なときに、関連 ADR を読む。全件を毎回読む必要はない。現在の仕様・手順から該当 ADR へリンクする。

**作るとき:** 複数の選択肢があり、設計・品質・運用へ継続的に影響する判断を残す。開発フローや文書管理の方針も含むが、誤字修正や既定手順の実施には作らない。調査中から同じ ADR に記録し、機能固有の調査も spec・plan から参照する。

**書く内容:** [採番・配置のルール](documentation-guide.md#adr-の形式)と[テンプレート](adr/_template.md)に従い、説明文を実際の内容へ置き換える。作成日は固定し、更新日は変更日とする。日付は `YYYY-MM-DD` を使う。

- **背景:** 決めたいこと、必要な理由、制約。要求本文は参照する。
- **調査:** 根拠となる資料・参照日・版、結果と限界。資料・ソース確認と実測を区別し、実測には環境・入力・手順・証拠を残す。
- **意思決定:** 比較した候補、選択理由、不利益、根拠と仮定。未決定なら不足する情報を書き、結論を捏造しない。
- **影響:** 仕様・実装・運用への影響と反映先、見直す条件。確定事項・見込み・未確定を区別する。

費用や環境変更を伴う検証は事前に許可を確認する。詳細ログや既存の調査結果は複製せず参照する。

**状態と変更:** 調査中・判断待ちは `ドラフト`。承認されたら `承認済み` とし、判断日と確認記録を残して現在の仕様・手順へ反映する。記録の作成だけを反映完了とはしない。

採用せず検討を終えた案は、理由を残して `廃止済み` にする。承認済み判断の実質的な変更は後継 ADR に記録し、その承認時に旧 ADR を廃止済みにして相互リンクする。過去の判断理由は書き換えない。

Spec Kit の標準アセットは直接改変せず、共通文書の読込不足が確認された場合にプロジェクト固有の override または拡張を検討する。初期化や指示の配置だけで参照が実行されたと推測しない。
