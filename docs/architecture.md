# アーキテクチャ

設計前のメモ。現在の技術方針と、複数の feature をまたいで決める必要がある論点をまとめる。まだコンポーネント構成や保存方式を確定していない。

## 現在の技術方針

評価対象のエージェントは Copilot SDK 経由で実行する。実際の Copilot の動作を比較したいので、独自のエージェントループへ置き換えない。SDK の版は固定・記録し、対応する CLI ランタイムの版を比較条件にできるようにする。

標準の LLM 判定を行う評価器も Copilot SDK を利用する方向で考える。利用者が実装する評価器は別 API を使えてよく、評価対象の実行経路とは区別する。

Git や Azure は取得元・実行先の具体例として扱う。すべての環境に SSH・VM・Linux コンテナがあるとは仮定しない。実行・評価・環境管理に [既存 OSS](adr/001-evaluation-tools.md) を使うかは未決定。

概念と不変条件は [ドメインモデル](domain-model.md)、満たすべき振る舞いは [各 spec](../specs/README.md)、対応環境と安全性は [共通非機能要件](nonfunctional-requirements.md) を参照する。

## 最初の設計で答える問い

### 誰が実行を持ち続けるか

開始 CLI が終了した後も比較を継続し、別の操作で状況確認・停止・再開するには、どの処理が実行状態を所有するか。将来の遠隔実行で接続が切れても、二重起動や後片付け漏れを起こさない責任分担が必要になる。

まずローカル比較と実行管理を一緒に検討し、状態遷移、停止完了、途中結果の取得、障害後の照合を決める。常駐サーバーの採用を前提にはしない。

### 記録と環境をいつ保存・解放するか

再試行時に消費済み使用量や失敗履歴を失わないため、何をどの時点で保存するか。終了した環境を使う評価があるので、記録回収・評価・後片付けの順序も必要になる。通常の成果物保存と、指定された調査用の環境保持を分けて設計する。

データ形式、保存先、保持期間、遠隔回収はこの責任分担を踏まえて選ぶ。実装後は型・スキーマを参照し、同じ構造をここに転記しない。

[Task Run の意味と関係](domain-model.md#実験タスクと実行)に従い、準備失敗を含む個々の実行から条件と証拠へたどれる保存を設計する。実行を束ねる単位の保存配置を、比較対象の制約にしない。環境のメタデータ・識別子・ハッシュ等を何に付与し、参照先をどこまで保持するかは未決である。

持ち込まれた指示・設定については当時の内容を読めることを前提とし、内容の保存と不変の版への参照の選択、重複排除、秘密情報の除外、参照先の保持を設計する。ハッシュの記録だけを内容の保持とみなさない。

### SDK の自由な指定と本体の管理をどう両立するか

利用者が SDK 設定や primitives を渡しても、イベント記録・計測・停止制御が意図せず失われないようにするには、どの設定を本体が管理するか。互換性と衝突時の扱いを調べ、適用不能な指定を黙って無視しない契約を決める。

使用量イベントの取得範囲と課金単位も確認する。欠測や停止前の最後のモデル呼び出しによる超過を、料金ゼロや厳密な事前上限として扱わない。

キャッシュ利用量をどの粒度で条件・時刻・呼び出しへ対応づけられるかも調べる。条件の偏りを抑える実行順序と並列上限の両立、提供側キャッシュの影響は、宣言だけで制御・観測可能とみなさない。

### Windows と Linux でどこまで環境を制御できるか

配置物・準備手順・サービス・モックをどう渡し、各試行の初期状態を作るか。準備済み環境の再利用、実行先への割当、認証情報の受け渡し・破棄も含めて確認する。

準備処理・エージェント・評価処理の権限と通信経路を調べ、ツールの公開制限と実際の通信制限を区別する。制限を強制できない実行先での扱いは、実現能力が分かってから判断する。

### 実験の記述と準備手順・評価器の拡張をどう扱うか

共通設定と条件差分、実験ディレクトリ、配置・配布形式を、実験の作りやすさから決める。ファイルやコードは Experiment の表現方法として設計し、独立したドメイン概念を追加しない。利用者が実装する準備手順と評価器は、実行時点・入力・出力・失敗時の扱いが異なるため、それぞれの契約を定める。モック・実行先の接続も必要な契約だけを定め、初期から汎用プラグイン基盤や構成生成機能を作るわけではない。

利用者によるエージェント経由の操作も想定する。人間向けには要点や差分で認知負荷を抑えつつ、操作を代行するエージェントが明示的な条件・状態を網羅的に取得できるようにする。作成時の省略や再利用と、記録の網羅性は別に扱う。共通設定・差分の解決方式や操作インターフェースは未決である。

タスク依頼を設定上のどこで指定するか、タスクの分類をどう表すかは未決。タスク依頼は必須のプロンプトと任意のアタッチメントで表し、SDK のメッセージ送信へ対応づける。2026-09-13 に確認した [SDK の MessageOptions](https://github.com/github/copilot-sdk/blob/main/nodejs/src/types.ts) には必須の `prompt` と任意の `attachments` があり、ファイル指定に対応する。これは公開型の確認であり、採用版での添付内容の読み込み、ツール無効時の挙動、遠隔実行時のパス・転送、保存時点は未検証である。共通の文章をプロンプトへ付け足す仕組みは前提にしない。Experiment と Experiment Run の識別・保存方式は設計で定め、調べたい問いや目的のための独立した管理単位は設けない。

比較の基準となる構成の指定方法や、選んだ結果の組み合わせに名前を付けて保存する機能の採否は未決。比較結果・評価結果の形式と合わせて検討する。

これらの問いに答えるための調査と採用理由は、テーマごとの [ADR](documentation-guide.md#adr-の形式) にまとめる。決まった全体構造は本書へ反映し、feature の plan はその構造への変更・追加を記載する。
