# 001: 既存の評価ツールと再利用の検討

- 状態: 承認済み
- 作成日: 2026-09-12
- 更新日: 2026-09-12

## 背景

Copilot のモデルやカスタマイズを比較する製品を考える中で、既存 OSS と何が違い、新しく作る価値がどこにあるかを確認した。

Waza の調査後は、スキルに限らない primitives 全般、細かなモデル設定、遠隔実行、隔離・モックと環境管理の組み合わせを強みと考えた。しかし Harbor にも近い機能があり、Harbor ベースで実現できるかを調べたうえで、製品として重視する価値と基盤の採否を分けて判断する必要が生じた。

## 調査

2026-09-12 の資料・ソース確認に基づく。

Waza

- [microsoft/waza](https://github.com/microsoft/waza) はスキル中心の評価ツールで、モデル比較、MCP モック、作業用ファイルの配置、評価前後の処理が重なる。
- 確認した版では [設定スキーマ](https://github.com/microsoft/waza/blob/611250c6b2eb288880307b27c424d278d2f7211e/schemas/eval.schema.json) は `skill` を必須とする。[SDK 実行処理](https://github.com/microsoft/waza/blob/611250c6b2eb288880307b27c424d278d2f7211e/internal/execution/copilot.go)の effort 指定や primitives の通常動作を保つ適用には、不足または未確認の範囲がある。
- 作業ディレクトリの分離と OS・通信・サービスの隔離は同じではない。また、評価基盤のライフサイクル hooks を、評価対象の Copilot hooks の適用機能とはみなせない。遠隔の実行管理については [JSON-RPC 処理](https://github.com/microsoft/waza/blob/611250c6b2eb288880307b27c424d278d2f7211e/internal/jsonrpc/handlers.go) も確認対象とした。

Harbor

- [Harbor](https://github.com/harbor-framework/harbor) は環境を伴うタスク評価と遠隔 sandbox を扱う。[確認した Copilot CLI アダプター](https://github.com/harbor-framework/harbor/blob/d8cfe6b6fd463fc1f2a84abf8f1406f46e70c621/src/harbor/agents/installed/copilot_cli.py)にはモデル・effort 指定があり、環境構築・遠隔実行・評価という組み合わせ自体は本製品固有ではない。
- SDK も CLI のランタイムを操作するため、CLI と SDK の違いだけを差別化とはしない。必要な設定の適用・記録、実行中の計測・制御が既存アダプターや拡張で足りるかが論点となる。
- 確認した標準集計は effort や指示の違いをキーに含まず、条件別のジョブ分離や独自集計が必要になる。AIC・料金の計測、再試行込みの累積使用量上限と失敗履歴の保持にも追加対応が必要だった。primitives の通常の適用動作や Windows の実務タスクへの適合には未確認事項が残る。
- 導入負担も判断材料とした。ただし、大量の依存導入は調査時の過剰な `--group dev` 指定の影響を含む。通常版の導入量は未測定で、テストは中断したため実行検証の完了とは扱わない。

## 意思決定

新しい評価エンジンを作ることではなく、GitHub Copilot の比較・改善を一通り行える、使いやすい製品に価値を置く。具体的には次を重視する。

- Copilot の model・effort・primitives を比較条件として扱い、品質・トークン・AIC・料金を対応づける。
- 見やすいダッシュボードで条件間の差から個々の試行の指示・ツール応答・変更ファイル・失敗理由へ進み、次に何を変えるか判断できるようにする。
- 環境準備、開始、進行確認、停止、再実行、後片付けを、別々の道具で組み立てずに扱えるようにする。
- Windows で画面や CLI が動くだけでなく、Windows 固有のビルドツールや PowerShell を使う実務プロジェクトを実行・評価できるようにする。

この製品の方向性を承認する。Harbor を必須基盤にする判断は保留し、採用・拡張と、設計を参考にした独自実装を引き続き比較する。既存基盤を再利用しても製品価値は失われない。既存ツールよりどれだけ使いやすいかは未検証であり、機能がない、実現できないという断定を差別化の根拠にしない。

## 影響

- 機能の有無だけでなく、同じ比較を用意し、結果から原因を調べ、次の実験へ進むまでの手間を設計・検証の対象にする。
- Windows の実務タスクは初期から設計・検証に含める。CLI ファーストは維持し、ダッシュボードの価値と提供時期を分けて扱う。
- 基盤選定では追加実装量と導入・運用・互換性維持の負担を比べる。自作の方が総工数まで小さいとは決めつけない。具体的な依存追加や方式変更は未確定。

現在の製品方針は [プロダクトビジョン](../product-vision.md)、実現方法は [アーキテクチャ](../architecture.md) を正本とする。
