# プロダクトビジョン

copilot-eval は、GitHub Copilot のモデル・ハーネス・カスタマイズを、自分の作業で比較し、挙動の理解と改善に役立てるためのツール。

## 解決したいこと

Copilot のモデル、effort、指示、スキルを変えても、普段の利用感や一回の成功だけでは効果を判断しにくい。品質が上がったのか、使用量が増えただけなのか、別の指示と干渉していないかを確かめたい。

対象は Copilot を利用・カスタマイズする利用者。実験のための環境準備、条件の固定、実行、記録、採点、集計を個別に組み立てずに、自分のプロジェクトで比較を始められるようにする。

## 提供したい体験

比較例から始めても、自分の資料・コード・primitives を持ち込んでもよい。手元のマシンでも離れた実行先でも、必要なサービスを含む環境を用意し、何を変えるかを明示して同じタスクを実行する。評価ポイント別の可否や rubric 点数と、トークン・AIC・料金を見比べる。

見やすいダッシュボードで条件間の差を捉え、気になったら個々の試行の指示・ツール応答・変更ファイル・失敗理由へ進み、設定を直してもう一度試す。環境準備から開始・進行確認・停止・再実行・後片付けまでを一続きに扱う。製品はこの反復を支え、カスタマイズの採用や改善の判断は利用者が行う。

- 同じ資料から書かせた文章で、モデルごとの日本語の自然さを比べる。
- 自分のプロジェクトのレビューで、モデルや effort による発見精度と使用量の違いを調べる。
- スキルの変更やコマンド出力の圧縮で、精度を落とさず使用量を減らせるか確かめる。
- 同じタスク・モデル・設定で Copilot CLI（ハーネス）のバージョンを変え、進化による動作・品質・使用量の変化を調べる。
- 複数のタスクでモデルを比較し、独創性や指示への忠実さなど、モデルの特徴として語られる仮説がどのタスク・条件で成り立つかを確かめる。

対話的に試す場合も、開発作業に継続的な評価を組み込む場合も、この比較を使えるようにする。別途データセットを管理することや Git の利用は必須にしない。具体的な比較例と受入れ条件は [機能仕様](../specs/README.md) で扱う。

## この製品の価値

### 利用者が得る価値

モデル・ハーネス・カスタマイズの違いを、品質・使用量・料金で定量的に捉え、理解・選択・改善の判断に使える。評判や一度の成功だけに頼らず、自分のタスクと条件で確かめられる。

各回のばらつきや失敗・欠測も含めて元の記録までたどり、効果がない、悪化した、まだ判断できないことも分かる。一つの総合点や自動的な勝者選定に判断を委ねない。

### その価値をどう届けるか

GitHub Copilot に最適化し、構成の指定、環境準備、実行管理、比較、原因調査を一つの使いやすい製品にまとめる。Linux と Windows の実務プロジェクトを持ち込み、見やすいダッシュボードから次の試行へ進めるようにする。Windows 対応は画面や CLI の起動だけでなく、Windows 固有のツールを使うタスクの実行・評価を意味する。

本体の内部実装を知らなくても、設定とサンプルから自分の比較を用意でき、標準で足りない処理は実験に合わせて追加できるようにする。

新しい評価エンジンを独自に作ることが目的ではなく、内部で既存基盤を使っても、この価値は変わらない。このアプローチを選んだ背景と既存 OSS との比較は [ADR 001](adr/001-evaluation-tools.md) に残す。

## 対象にしないこと

- 任意のエージェント製品を動かす汎用基盤。
- 実行をまたぐ記憶の継承、過去の実行結果による自動キャッシュ、旧形式との互換・移行。
- 本体がカスタマイズを書き換え続ける自動探索や、モデルの普遍的な優劣の保証。
- 外部情報源やモデル提供側の変化まで含めた、出力の完全な再現性。

具体的な機能と提供段階は [機能仕様](../specs/README.md)、実現方式は [アーキテクチャ](architecture.md)、対応環境や導入負担の条件は [共通非機能要件](nonfunctional-requirements.md) で扱う。
