# 文書管理ガイド

必要な情報をどこに書き、どう重複を避けるかのガイド。作業の進め方と ADR を読むタイミングは [開発フロー](development-workflow.md) を参照する。

## 文書管理の原則

次の判断や実装、結果の理解に使う情報を書く。文書を揃えたり空欄を埋めたりすること自体を目的にしない。

- **構造と名前に意味を持たせる。** ディレクトリ構造・ディレクトリ名・ファイル名から、扱う話題と役割を予測できるようにする。分類のためだけの階層や、内容の所在が分からない曖昧な名前を増やさない。
- **各ファイルを無駄に肥大化させない。** そのファイルの役割に必要な情報だけを置く。行数上限は設けず、独立した話題や参照目的が生じたときに分割する。分量を減らすために必要な情報を削らない。
- **導出できる情報を重ねて書かない。** 情報 A と B から C を導出でき、A・B・C が同じファイルにある場合は C を削除する。A と B が別ファイルにある場合は、両者の関係と C を説明する文書を用意するか、A・B の関連が分かる記述とリンクを埋め込む。関係を説明する文書へ A・B の本文を複製しない。C に独立した判断や追加の前提が含まれる場合は、単なる導出結果と区別する。
- **AGENTS からすべての文書へたどれるようにする。** [ルートの AGENTS](../AGENTS.md) から索引や関連文書のリンクを経由して、`docs/` 配下の任意のドキュメントへ到達できる状態を維持する。すべてを AGENTS に直接列挙せず、[文書索引](README.md) と各テーマの索引で案内する。配置図やリンクでないパス表記だけでは到達経路とみなさない。

文書の追加・移動時は、適切な索引のリンクも同時に更新する。リンク到達性は必要なときに文書を探せる条件であり、毎回すべての文書を読む指示ではない。

共通フレーム2013などの枠組みは、検討漏れを点検する観点として使う。そこにある工程や成果物を、そのままディレクトリ・テンプレート・承認手続きへ変換しない。

## 配置と役割

共通文書は `docs/`、機能固有の要求と設計は `specs/`、プロジェクト原則は `.specify/memory/constitution.md` に置く。調査は何らかの意思決定のために行うため、共通・機能固有を問わず `docs/adr/` に判断とまとめる。独立した research 文書は作らない。

| 保存先 | 書くこと |
| --- | --- |
| [product-vision.md](product-vision.md) | 長期に維持する製品の目的・価値・対象範囲。提供順序や実装計画は含めない |
| [domain-model.md](domain-model.md) | 製品で区別する概念、その関係と守るべきルール |
| [architecture.md](architecture.md) | 現在の技術方針、決まった全体構造、設計上の未解決事項 |
| [nonfunctional-requirements.md](nonfunctional-requirements.md) | 機能をまたぐ対応環境・導入負担・安全性等の条件 |
| [development-workflow.md](development-workflow.md) | Spec Kit の使い分け、変更とレビュー、ADR の運用 |
| [constitution.md](../.specify/memory/constitution.md) | プロジェクトの判断原則と、その変更手続き |
| [specs/](../specs/README.md) | 機能ごとの要求、設計、実装作業。共通文書を参照し、追加・変更だけを記述 |
| `docs/adr/` | 判断したい問い、調査方法・証拠・結果・限界、選択肢・判断理由・影響。現在の方式は architecture 等へ反映 |
| [AGENTS.md](../AGENTS.md) | エージェントが必要な正本へ進むための入口。原則・手順本文はコピーしない |
| [README.md](README.md) | 文書の索引。各文書の内容を再要約しない |

配置を変更しても、同じ情報の正本を二つにしない。共通文書は複数機能に共通する意味・制約・設計を扱い、feature 文書は対象機能の要求と実現方法を扱う。

ビジョンは開発の進捗や提供順序の変更では書き換えない。競合 OSS の登場や利用者の課題の変化など、製品の存在意義や価値の前提が変わったときに見直す。提供段階は機能仕様側、実装計画は各 feature の plan・tasks で扱う。

### Spec Kit の feature 内の文書

| 保存先 | 内容 |
| --- | --- |
| `specs/<feature>/spec.md` | 機能の WHAT / WHY、要求と受入れシナリオ |
| `plan.md` | 実現方針、技術制約、共通設計への適合と変更提案 |
| `data-model.md` | 対象機能のデータ設計。共通ドメインの別定義ではない |
| `contracts/` | 必要な外部インターフェースの契約 |
| `quickstart.md` | 機能を検証するシナリオと手順。製品全体の利用ガイドとは別 |
| `tasks.md` | 実装・検証作業と進捗 |
| `checklists/` | 要求等の品質確認。動作検証の証拠とは別 |

後続工程の成果物は、必要な工程に進んだ時点で作成する。既存IDの移行先は [specs の索引](../specs/README.md) に残し、改番や別の要求台帳の作成はしない。

### ADR の形式

ファイル名は `001-{slug}.md`、先頭の見出しは `# 001: {title}` とする。番号は `docs/adr/` 内で 001 から順に採番し、slug は内容を表す英語の kebab-case にする。既存番号は変更・再利用しない。[テンプレート](adr/_template.md) は採番対象外とする。

メタデータと本文の見出しはテンプレートの規定フォーマットに従う。各節に書く内容と状態の扱いは [開発フロー](development-workflow.md#adr-を読む残す) を参照する。

### ツール管理ファイル

`.specify/memory/constitution.md` はプロジェクトが編集する原則の正本。一方、標準の `.specify/templates/`、`scripts/`、連携マニフェスト、workflow 登録と `.github/skills/speckit-*/` は導入済みツールの管理対象とする。`.specify/feature.json` は作業対象を示す設定であり、仕様や進捗の台帳ではない。

独自テンプレートが必要になった場合だけ `.specify/templates/overrides/` を使う。今回の移行では追加していない。共通文書のコピーを `.specify/memory/` に作らず、必要な正本を参照する。

導入済み Spec Kit の標準コマンドには `research.md` の生成・参照が残っている。ADR に統一する本方針への対応は未実施のため、plan 実行前に生成先と後続コマンドの参照方法を調整する。標準アセットを直接書き換えない。

## 指示・原則・要求の関係

差異を発見したら、どちらかを黙って書き換えず、対象文書・矛盾・影響を示す。constitution に反する要求や設計は、要求・設計の修正か、明示的な原則変更として扱う。AGENTS にある作業指示を根拠に、製品要求を変更しない。

Spec Kit 内で constitution を判断基準とすることは、エージェント基盤のシステム指示を上書きする意味ではない。原則の強制が必要な箇所は、テストや CI 等で確認する。更新時の影響確認と承認は [開発フロー](development-workflow.md) に従う。

## 書くとき・更新するとき

- 新規ファイル名は英語の kebab-case を基本とし、README・AGENTS は慣例に従う。本文は日本語とする。
- 共通ドメインは話題ごとに「定義表・関係・ルール」を置く。定義表は用語・英語名・意味・短い例、関係は概念間の対応、ルールは同一性・状態変化・不変条件を扱い、同じ説明を重ねない。意味そのものの未決事項は該当箇所に残し、実現方法の未決事項は設計側へ分ける。
- 図が理解を助ける節だけ、任意のサブセクション `### 概念図` を追加する。図は `mermaid` コードブロックで記述し、種類は表したい関係に合わせて選ぶ。全節への追加や、図のためだけの説明の複製は行わない。
- Spec Kit の feature 文書は、読込処理との互換性のため標準見出し・ファイル名を維持する。独立した UC 文書と全く同じ書式にする必要はない。
- 要求とその受入れ条件は関連づけ、提案・合意・実装・検証を区別する。ファイルが存在するだけで承認済みとは扱わない。
- 未決事項は、何をなぜ決める必要があるかを書く。理由のない TBD 欄、担当・期限・承認の一律の記入枠は作らない。
- 利用手順は実際に動く機能ができた時点で、実行確認した最短手順から書く。将来の画面や運用のためだけに空の文書を作らない。
- 型・スキーマ・テストから分かる詳細は転記せず参照する。調査と判断は一つの ADR にまとめ、spec や plan から参照する。
- 資料調査、静的ソース確認、実行検証を区別する。検証は方法・前提・証拠・結果・限界を残す。詳細ログは参照先で管理する。
- 更新後は相対リンク、AGENTS から各ドキュメントへの到達性、ID の重複・未定義参照、意味の矛盾、正本の重複、導出情報の冗長さを確認する。到達性の検証はファイルの存在確認だけでなく、リンクを再帰的にたどって未到達文書がないか確認する。移行時は情報の対応と欠落も確認する。
- 検証のための重い依存導入、有料モデル実行、クラウド作成は、必要性と許可を確認してから行う。実施できない検証を明示する。
- 完了報告は変更内容、実施した検証、未確認事項、残課題を区別する。要求の受入れ判断と自動テストの成否を混同しない。
